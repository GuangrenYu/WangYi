# 测试输入数据分类与工作流进度

统计时间：2026-07-18

本文说明 `data/test_cases` 中各类输入数据的来源、集合关系，以及当前项目对不同数据所达到的工作流阶段。统计按 CVE 编号去重，CVE 编号统一转为大写；PCAP 文件同时按文件数和唯一 CVE 数统计。

## 1. 结论先行

- `未在工作流实现.txt` 是当前主要的历史待处理集合，共 1,228 个唯一 CVE。它由 A/B/C 三个信息完整度子集无交集地组成。
- `未测试_已有本地环境.txt` 不是主清单的子集，而是从本地 Vulhub 环境集合中排除已有记录后得到的待测集合，共 184 个 CVE；184 条都能在本地找到对应 Compose 定义。
- `data/cve/pcaps/漏洞类` 是已归档的历史攻击流量/抓包资料。当前目录有 1,422 个唯一的规范 CVE 名称，和 1,228 条主清单没有交集；因此不能把历史 PCAP 数量直接当成主清单的完成量。
- `.pending` 中的 `CVE-2024-1071.pcap` 尚未进入正式 `漏洞类` 归档。它是当前 PCAP 与主清单唯一的 CVE 交集，但按项目防重逻辑不会被正式归档集合识别。
- 当前 `output/<CVE-ID>/result.json` 快照显示，主清单已有 430/1,228 条产生结果目录，其中 22 条为 `CAPTURE_SUCCESS`；其余主要停在环境、外部搜索、非 HTTP 或仅通用 IPS 命中阶段。剩余 798 条没有当前结果目录。
- “有本地 Compose”“执行过工作流”“产生 PCAP”“验证成功”是四个不同状态，本文分别记录，不合并为一个完成标记。

## 2. 输入数据大分类

### 2.1 主任务集合：历史上未在工作流实现

来源文件：[`未在工作流实现.txt`](./未在工作流实现.txt)

| 子类 | 文件 | 数量 | 含义 | 工作流定位 |
|---|---|---:|---|---|
| A 类 | [`A_信息丰富.txt`](./A_信息丰富.txt) | 404 | 漏洞描述、参考资料或 PoC 线索相对丰富 | 主测试集，最适合先验证检索、PoC 和判定链路 |
| B 类 | [`B_信息中等.txt`](./B_信息中等.txt) | 574 | 信息量中等，需要 Agent 补全更多上下文 | 抽样验证 Agent 的补全能力 |
| C 类 | [`C_信息较少.txt`](./C_信息较少.txt) | 250 | 公开线索较少或复现前置条件不清楚 | 后置极端样本，优先级低于 A/B |

占比约为 A 32.9%、B 46.7%、C 20.4%。这里的 A/B/C 是输入信息完整度分类，不是项目最终成功等级。

### 2.2 本地环境待测集合：由 Vulhub 集合做减法

来源文件：[`未测试_已有本地环境.txt`](./未测试_已有本地环境.txt)

当前本地 `third_party/vulhub` 约有 246 个唯一 CVE、328 个 Compose 文件。根据现有生成记录，这个清单的形成口径是：

```text
本地 Vulhub 唯一 CVE                         246
- 生成清单时已有批测记录                     49
= 初始“未测试且已有环境”集合                 197
- 历史成功 PCAP 中发现的已完成项              13
= 当前未测试_已有本地环境.txt                 184
```

当前 184 条的核对结果：

| 检查项 | 结果 | 说明 |
|---|---:|---|
| 清单 CVE | 184 | 唯一编号，无重复 |
| Vulhub Compose 精确命中 | 184/184 | 环境发现层覆盖完整 |
| Compose 配置有效 | 183/184 | `CVE-2017-5223` 缺少当前目录中的 `.env` |
| 镜像全部已缓存 | 2 | 见 [`未测试_已有本地环境_已缓存介质.txt`](./未测试_已有本地环境_已缓存介质.txt) |
| 与主清单交集 | 0 | 不是 `未在工作流实现.txt` 的子集 |
| 与正式 `漏洞类` PCAP 交集 | 0 | 生成待测集合时已排除历史成功项 |

同一批中的缓存介质子集为 `CVE-2020-11978` 和 `CVE-2020-17526`。最新两条批测都完成了任务记录，但最终为 `INFRASTRUCTURE_FAILED`，没有进入成功归档；因此“镜像已缓存”只表示越过镜像获取这一关，不表示服务已就绪或漏洞已验证。

### 2.3 11 条优先本地环境样本

[`A_优先复现_有本地环境.txt`](./A_优先复现_有本地环境.txt) 与 [`已有环境.txt`](./已有环境.txt) 内容集合完全相同，都是 11 条，并且全部属于 A 类。这是早期的优先复现样本，不等同于当前 184 条本地环境待测集合。

这 11 条已具备真实产品/组件的 Vulhub Compose，项目曾经对其执行过批测。历史批测记录中有 2 条出现 `TARGET_ORACLE_SUCCESS`，但对应批测记录没有正式 PCAP 路径；当前 `output/<CVE-ID>/result.json` 又被后续运行覆盖为 6 条 `INFRASTRUCTURE_FAILED` 和 5 条 `NOT_HTTP_VULN`。因此本批应描述为“环境材料已具备、工作流曾到达验证阶段”，不应描述为“11 条均已抓包成功”。

### 2.4 历史 PCAP 与无 CVE 编号流量

来源目录：[`../cve/pcaps`](../cve/pcaps)

当前统计：

| 范围 | 文件数 | 唯一规范 CVE | 说明 |
|---|---:|---:|---|
| `漏洞类` 全部归档 | 2,524 | - | 正式历史资料目录 |
| `漏洞类` 中规范命名的 CVE PCAP | 1,455 | 1,422 | 文件名符合 `CVE-YYYY-NNNN...` |
| `.pending` | 1 | 1 | `CVE-2024-1071.pcap`，待归档 |
| `pcaps` 总文件数 | **2,525** | **1,423** | 含 `.pending` |
| 无规范 CVE 名称或非 CVE 文件 | 1,069 | - | 不能由当前 CVE 防重逻辑自动关联 |

1,069 个非规范命名文件主要来自以下三类无 CVE 或厂商编号数据：

| 目录/资料批次 | 文件数 | 当前用途判断 |
|---|---:|---|
| `AI工作流生成的无cve漏洞数据(549条)` | 548 | 无 CVE 编号的攻击流量资料 |
| `AI工作流生成的盛邦无cve漏洞数据(302条)` | 302 | 盛邦/厂商编号攻击流量资料 |
| `AI工作流生成的无cve漏洞数据(217条)` | 217 | 无 CVE 编号的攻击流量资料 |
| 两个单独的历史命名文件 | 2 | 一个带时间后缀的 CVE 文件、一个厂商编号文件 |

按项目现有语义，正式 PCAP 代表已经完成发包并完成抓包归档；但对于无 CVE 编号的资料，项目无法自动把它们关联到某个 CVE 的 NVD、PoC、环境和验证结果。它们更适合作为流量、IPS 规则或厂商漏洞数据集，而不是当前 CVE 工作流的直接输入。

补充：当前防重代码使用 `CVE-YYYY-NNNN...` 的搜索而不是完整文件名匹配，因此 `CVE-2020-8813_164820.pcap` 这类带后缀文件仍可能提取出 CVE-2020-8813；这不改变其“非规范命名”的资料属性。

## 4. 工作流阶段定义

当前项目的主链路为：

```text
输入校验
  -> NVD 查询
  -> HTTP/Web 类型判断
  -> 攻击环境发现/启动
  -> 本地知识库和 References 检索
  -> TriggerAgent 建模
  -> 多源 PoC 候选收集与 CriticAgent 评审
  -> 发包、IPS/目标侧 Oracle 验证
  -> PCAP/PoC/结果归档
  -> 环境回收
```

对应实现主要在 [`cve_hunter/graph.py`](../../cve_hunter/graph.py)、[`cve_hunter/agents.py`](../../cve_hunter/agents.py)、[`cve_hunter/verification.py`](../../cve_hunter/verification.py) 和 [`main.py`](../../main.py)。

| 阶段 | 通过标志 | 含义 |
|---|---|---|
| 输入校验 | `input_validated=passed` | CVE 格式被工作流接受 |
| 情报加载 | `nvd_loaded=passed` | NVD 描述、CVSS、References 等已加载 |
| 协议分类 | `http_classified=passed` | 已判断 HTTP/Web 或非 HTTP |
| 环境规划 | `environment_planned` | 找到或规划了 Vulhub/Compose 等环境候选 |
| 环境就绪 | `environment_ready=passed` | 容器启动并通过适用的 healthcheck/TCP/HTTP 检查 |
| PoC 候选 | `candidate_collected=passed` | 得到可执行 Raw HTTP 或 Nuclei 候选 |
| 验证执行 | `attempt_history` 有记录 | 至少尝试过候选并记录请求、响应、IPS/Oracle 结果 |
| 成功归档 | `status=SUCCESS` | 当前 CVE 有足够的 IPS 精确命中或目标侧 Oracle 证据 |
| PCAP 归档 | `data/cve/pcaps/漏洞类/**/*.pcap` | 成功流量已形成正式 PCAP 文件；`.pending` 不计入正式防重集合 |

`IPS_GENERIC_MATCH_ONLY` 只表示检测到通用攻击流量，不能算当前 CVE 验证成功。`NOT_HTTP_VULN`、`WEB_SEARCH_FAILED` 和 `INFRASTRUCTURE_FAILED` 也分别代表不同的停止位置，不能统一写成“PoC 失败”。

## 5. 不同分类目前做到哪一步

### 5.1 主清单整体：1,228 条

按当前 `output/<CVE-ID>/result.json` 快照统计：

| 当前状态 | 数量 | 所达到的阶段 |
|---|---:|---|
| `CAPTURE_SUCCESS` | 22 | 当前 CVE 验证成功并完成成功结果归档 |
| `INFRASTRUCTURE_FAILED` | 171 | 多数停在环境启动、目标或验证基础设施 |
| `IPS_GENERIC_MATCH_ONLY` | 123 | 已有流量/IPS 检测，但未精确匹配当前 CVE |
| `WEB_SEARCH_FAILED` | 75 | 已推进到外部 PoC/网页搜索，但搜索链路失败 |
| `NOT_HTTP_VULN` | 33 | 已完成类型判断，因非 HTTP 不进入 HTTP 验证 |
| `HTTP2PCAP_SERVICE_FAILED` | 6 | 已到发包服务调用，但服务调用失败 |
| 有结果目录合计 | **430** | 剩余 798 条暂无当前结果目录 |

这说明项目对主清单已经具备批量处理、失败归因和少量成功闭环能力，但还没有把 1,228 条全部推进到验证阶段。正式 `漏洞类` PCAP 与该主清单没有交集，不能用 1,422 个历史 PCAP 替代这 22 条当前结果。

### 5.2 A/B/C 信息完整度分组

以下仍然是当前 `result.json` 快照，不是不可变的历史累计统计；重新运行同一个 CVE 会覆盖其结果目录。

| 分组 | 总数 | 有结果目录 | `CAPTURE_SUCCESS` | 主要停止状态 |
|---|---:|---:|---:|---|
| A 信息丰富 | 404 | 247 | 8 | 171 环境/基础设施、31 非 HTTP、19 通用 IPS、17 搜索失败、1 发包服务失败 |
| B 信息中等 | 574 | 143 | 14 | 75 通用 IPS、50 搜索失败、4 发包服务失败 |
| C 信息较少 | 250 | 40 | 0 | 29 通用 IPS、8 搜索失败、2 非 HTTP、1 发包服务失败 |

解释：

- A 类已经最完整地覆盖“输入校验、NVD、类型判断、环境尝试、PoC/验证和结果归档”这些路径，但环境基础设施仍是最大阻塞点。
- B 类已经有成功和通用 IPS 命中样本，说明 Agent 能在部分信息不足的情况下补齐 PoC 或验证线索；但大部分输入尚未执行，且搜索失败占比较高。
- C 类当前没有 `CAPTURE_SUCCESS`，主要价值仍是验证信息不足时的失败归因；不适合在 A/B 链路未稳定前直接扩大全量运行。

### 5.3 11 条已有本地环境优先样本

项目已经完成了这批的环境发现、NVD 加载、HTTP 分类和历史批量尝试；历史记录中部分任务曾到达目标侧 Oracle 判定，至少 2 条曾记录 `TARGET_ORACLE_SUCCESS`。但当前结果目录显示：

- 6 条因 Docker/环境就绪问题停止在 `INFRASTRUCTURE_FAILED`；
- 5 条被判定为 `NOT_HTTP_VULN`；
- 当前没有正式 `data/cve/pcaps/漏洞类/<CVE>.pcap` 对应项；
- 因此达到的是“有环境、曾执行、部分曾到达 Oracle”，不是“11 条全部 PCAP 成功”。

### 5.4 184 条未测试本地环境

这一类已经完成了环境材料层和预检层：184/184 找到 Compose，183/184 配置有效，2 条镜像全部缓存。真正的批量复现尚未展开：当前只有 8 条产生结果目录，其中 6 条停在 NVD 请求失败、2 条停在基础设施失败，没有成功项和 PCAP 项；2 条已缓存介质样本的最新批测也均为环境失败。

因此该类别当前阶段是：

```text
Vulhub 集合筛选 -> Compose 发现 -> 静态预检
                                     -> 大部分尚未进入 PoC/发包/验证
```

下一步应优先修复 `CVE-2017-5223` 的 Compose 配置问题，解决 Docker 镜像/服务就绪条件，再用少量低复杂度环境验证启动、健康检查、发包、归档和回收闭环。

### 5.5 已完成抓包的 PCAP 类数据

这类数据已经越过了当前工作流的“发包/抓包/流量归档”阶段，适合作为：

- 已有成功流量或历史攻击报文的回归资料；
- IPS 规则和流量识别的验证资料；
- 后续批量入口的成功项防重依据（仅限正式 `漏洞类` 目录中能从文件名识别 CVE 的文件）。

它不等价于：

- 对应 CVE 当前版本环境仍然可以重新启动；
- 当前 PoC 仍能复现；
- 目标侧 Oracle 仍然可以验证；
- 无 CVE 编号的厂商攻击流量可以自动映射回某个 CVE。

## 6. 当前项目能力边界

已经做到：

1. 统一解析 CVE 清单，支持单条、批量、继续执行和 HTTP/非 HTTP 预分类。
2. 完成 NVD 查询、协议分类、本地知识库检索、References 分析和多源 PoC 回退。
3. 支持从本地 Vulhub/Compose 发现环境，并记录环境 manifest、Agent 轨迹和里程碑。
4. 区分环境失败、NVD/搜索失败、发包服务失败、通用 IPS 命中和当前 CVE 成功。
5. 在获得足够验证证据后归档 PoC、结果和 PCAP，并按工作流拥有权回收已启动环境。

尚未做到：

1. 不能把所有 A/B/C 输入自动变成真实可运行环境；Compose 存在不代表镜像、初始化和服务健康都可用。
2. 不能用统一 HTTP 健康检查覆盖文件、UDP、数据库、消息协议或内核类漏洞。
3. 不能把通用 IPS 命中、一次 HTTP 响应或历史 PCAP 单独当作当前 CVE 的复现成功证据。
4. 无 CVE 编号的厂商流量还没有统一的 CNVD/厂商编号到 CVE 的关联层。
5. `未测试_已有本地环境.txt` 的 184 条尚未形成稳定的批量“启动—就绪—验证—回收”成功率。

## 7. 建议的后续顺序

1. 先以 A 类中已有输出但 `INFRASTRUCTURE_FAILED` 的样本定位 Docker、端口、初始化和健康检查问题。
2. 对 184 条本地环境先用预检结果筛出配置有效、镜像可用且复杂度低的样本，连续完成少量闭环后再扩量。
3. 单独处理 `.pending/CVE-2024-1071.pcap`：确认它是待归档成功结果还是临时抓包，再决定是否移动到正式归档目录；不要仅因文件存在就跳过复测。
4. 为无 CVE 抓包建立独立的厂商编号/漏洞名称索引，避免把它们强行塞入 CVE 工作流。
5. 统计成功率时使用 `result.json.status_code` 和 `output/batch/*.json`，将历史 PCAP 仅作为已归档流量证据和防重依据。
