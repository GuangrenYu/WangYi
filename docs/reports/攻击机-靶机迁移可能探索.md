# 攻击机–靶机迁移可能探索

生成日期：2026-07-20  
关联：`docs/reports/数据库非HTTP成功案例思路盘点.md`、`docs/plans/智能体能力蓝图.md`  
范围：当前已闭环的数据库非 HTTP 成功案例，若从「同机本地靶场」迁到「攻击机 ↔ 靶机」两机形态，能否复现、卡点在哪、怎么改。

---

## 0. 结论摘要

| 判断 | 说明 |
|---|---|
| **漏洞原理** | 三个成功案例在两机上**原则上都可复现**（2122 受靶机 memcmp/环境强相关） |
| **当前自动化默认路径** | **不能**直接等价迁移：默认假设攻击与靶场在同一台机器 |
| **执行器层** | Python DB 驱动直连，**本身支持远端 DSN** |
| **环境/策略层** | 绑定本机 compose、`local_lab`/`--local-container`，与两机模型不对齐 |
| **取证层** | 库内 oracle 跨机仍成立；pcap 变成「攻击机侧出站流量」 |

**一句话：**  
当前成功证明的是「授权本地靶场里，数据库非 HTTP 的抽取 → 执行 → 目标侧 oracle → 归档」链路成立；**不能写成「任意远程靶机开箱即复现」**。远程两机需要：策略切换 + 目标寻址 + 弱化本地 compose 依赖；（完整 1058）还要靶机出站回调。

## 1. 当前成功路径的真实形态

### 1.1 同机模型（现状）

```text
[同一台 Windows 主机]
  Python CVE Hunter
       │  psycopg2 / pymysql 直连
       ▼
  127.0.0.1:5432 / 3306  ← Docker 端口映射
       │
       ▼
  vulhub 容器内的 PostgreSQL / MySQL
```

### 1.2 隐含假设

| 假设 | 现状 |
|---|---|
| 目标可达 | `127.0.0.1` + 本地端口映射 |
| 执行策略 | `RUN_MODE=local_lab`，本机/私网默认允许 |
| 环境编排 | 攻击机本机 `docker compose up` |
| 抓包 | 攻击机 dumpcap 抓本机网卡（Loopback 等） |
| 凭证 | 文档/compose 默认弱口令 |
| 外连/监听 | 1058 简化版不需要；完整 dblink 版需要 |

### 1.3 两机模型（目标形态）

```text
[攻击机]  Python + DB 驱动 + 可选 dumpcap + 策略/编排
    │  网络：tcp/5432 或 tcp/3306（及可选回调端口）
    ▼
[靶机]    真实/容器化的漏洞版本数据库服务
```

### 1.4 当前成功案例清单（对照基线）

| CVE | 形态 | 本地闭环方式 | 关键证据 |
|---|---|---|---|
| CVE-2019-9193 | Postgres `COPY ... PROGRAM` | 单会话 SQL | `uid=...postgres...` |
| CVE-2012-2122 | MySQL 鉴权绕过 | `auth_bypass` 错误密码循环 | 第 N 次登录成功 |
| CVE-2018-1058 | search_path 提权 | `multi_session` 简化 marker | `cve-2018-1058-triggered` |

三者均达到：`数据库命中` + `可复现归档`。历史批测中曾失败（非 HTTP 不支持 / 情报失败 / 搜索失败），属于能力补齐后的闭环，而非「一直稳定远程成功」。

## 2. 分层：什么能迁、什么不能直接迁

| 层级 | 本地成功是否蕴含两机成功 | 说明 |
|---|---|---|
| 漏洞原理 | 基本蕴含 | 2122 依赖特定 memcmp/环境，靶机差异大 |
| 手工客户端打远端 | 通常能 | 网络 + 账号 + 版本满足即可 |
| 现有自动化默认路径 | **不蕴含** | 环境编排绑定本机容器 |
| multi_session 简化 1058 | 能 | 攻击机开两个会话连同一靶机即可 |
| 1058 完整 dblink | 额外依赖 | **靶机出站 → 攻击机监听** |
| 抓包进 repro | 攻击机侧能抓 | 含义变为跨机出站流量证据 |
| IPS 命中 | 无直接蕴含 | 取决于路径上是否有检测设备 |

## 3. 三个案例：两机可行性细拆

### 3.1 CVE-2019-9193（PostgreSQL 命令执行）

| 维度 | 两机是否可行 | 说明 |
|---|---|---|
| 协议利用 | **能** | 攻击机 `psycopg2` 连 `靶机IP:5432`，执行相同 SQL |
| 前提 | 需要 | 超户或 `pg_execute_server_program`；版本在受影响区间；5432 对攻击机开放 |
| 当前自动化 | **半通** | 执行逻辑通；`--local-container` 会在**攻击机**起 Docker，不是「只连远端」 |
| oracle | **能** | `SELECT` 返回 `uid=`，与是否本机无关 |

**结论：** 纯利用层最适合两机迁移。改 DSN 指向靶机 + 放行策略后，手工/半自动即可；完整自动需「远程目标模式」。

**最小远端 DSN 示例：**

```text
postgres://postgres:密码@靶机IP:5432/postgres
```

**迁移步骤（概念）：**

1. 靶机部署受影响 Postgres（或已有 vulhub 映射到靶机网卡）  
2. 攻击机策略允许该 IP  
3. 跳过本机 compose，直接 `execution_spec` + 远端 target  
4. oracle 仍为 `result_contains: uid=`  

---

### 3.2 CVE-2012-2122（MySQL 鉴权绕过）

| 维度 | 两机是否可行 | 说明 |
|---|---|---|
| 协议利用 | **能** | 错误密码反复登录是协议行为，不依赖「同机」 |
| 环境敏感 | **高** | 与 memcmp 实现/环境相关，靶机 OS 不同可能不稳定或失败 |
| 网络/中间件 | 需注意 | 防火墙、连接限速、IPS 可能拦截爆破式认证 |
| 当前自动化 | **半通** | 执行器可打远端；编排默认起本地容器 |

**结论：** 原理上两机可打；**成功率不等于本地 vulhub**，必须在靶机环境上单独验收。

**迁移风险：**

- 本地成功 ≠ 远程同类版本一定成功  
- 多次连接可能被安全设备封禁  
- 应用层负载均衡/代理可能改变认证路径  

---

### 3.3 CVE-2018-1058（search_path 提权）

#### A. 当前实现：简化 marker 版

| 维度 | 两机是否可行 |
|---|---|
| 低权植入 + 超户触发 | **能**（攻击机两个会话连同一靶机） |
| 依赖本机 Docker | 否（靶机已有用户/库即可） |
| oracle | marker 在靶机库内，攻击机 `SELECT` 可读 |

**结论：简化版两机完全可行。**

#### B. Vulhub 原版：dblink 外连偷密

```text
靶机超户触发 → dblink 连到攻击者监听地址 → 密码哈希外带
```

| 维度 | 两机是否可行 | 说明 |
|---|---|---|
| 流量方向 | 关键 | **靶机连出到攻击机**，不是攻击机单方面连入 |
| 网络 | 苛刻 | 靶机须能访问攻击机 IP:端口；NAT/防火墙常挡 |
| 当前代码 | **未实现** | 刻意用 marker 简化，未做完整 dblink 链 |

**结论：完整版两机「可以」，工程难度明显高于本地；自动化尚未覆盖。**

## 4. 系统各层：两机适配现状

### 4.1 执行器层（大体能）

- `execute_database_spec` / `auth_bypass` / `multi_session` 使用标准 DB 客户端  
- 不要求 DB 与 Python 同机  
- 只要 `target` / 环境 `target_url` 写成远端 host:port，协议利用可成立  

### 4.2 策略层（必须改配置）

| 靶机地址类型 | `local_lab` | `authorized_target` |
|---|---|---|
| `127.0.0.1` | 允许 | 需在 `TARGET_ALLOWLIST` |
| 私网 `10.x` / `192.168.x` | 一般允许 | 需白名单 |
| 已配置 allowlist 的 IP（如实验网） | 可过 | 可过 |
| 未白名单公网 | 拒绝 | 拒绝 |

两机复现前应明确：

1. **授权靶机**（书面/流程授权，不仅是技术可达）  
2. 优先 `RUN_MODE=authorized_target` + `TARGET_ALLOWLIST` 含靶机  
3. 或 `local_lab` 且靶机在私网（仍建议白名单收紧）  

### 4.3 环境层（默认不对齐）

| 场景 | 与当前默认是否匹配 |
|---|---|
| 攻击机本机起 vulhub 再打 | 匹配（现有成功案例） |
| 靶机已有 DB，攻击机只负责打 | **不匹配**；应禁用「必须本地起容器」 |
| 靶机上起 Docker，攻击机连靶机映射 IP | 可行，偏人肉/半自动 |
| `--local-container` | 语义是本机 Docker；失败不回退远程 |

### 4.4 抓包层（模型变化）

| 抓包位置 | 同机本地 | 两机 |
|---|---|---|
| 攻击机 dumpcap | 本机↔127.0.0.1 或 Docker 映射 | 攻击机→靶机的出站 TCP |
| 靶机入站全貌 | 同一台可见 | 攻击机默认看不到，需靶机抓包/镜像 |
| 成功判定 | 仍以 DB oracle 为主 | 同上；pcap 为辅证 |

数据库路径已具备 TCP 抓包（`cve_hunter/tools/tcp_capture.py`）：两机时抓的是**攻击机侧**流量，归档路径不变，但证据语义应标注为「attacker-side capture」。

### 4.5 凭证与前置

| 本地 vulhub | 真靶机 |
|---|---|
| 默认弱口令 | 常无默认口令 |
| 端口映射到本机 | 可能仅内网监听 |
| 无跳板 | 可能要 VPN/堡垒机 |

失败时更可能落到 **`缺前置条件` / `目标不可达`**，而不是 payload 无效。

## 5. 迁移条件清单（最小可行）

### 5.1 必须

1. **授权**：靶机在授权范围内，策略模式与白名单正确  
2. **网络**：攻击机 → 靶机 `tcp/5432` 或 `3306` 连通  
3. **版本/配置**：靶机软件版本与漏洞前提满足  
4. **寻址**：`execution_spec.target` 或环境目标为 `tcp://靶机IP:端口` / 完整 DSN  
5. **凭证**：可用账号（实验弱口令或授权测试账号）  

### 5.2 按案例附加

| 案例 | 附加条件 |
|---|---|
| 9193 | 超户或可 PROGRAM 权限 |
| 2122 | 靶机环境能触发 memcmp 缺陷；容忍多次认证尝试 |
| 1058 简化 | 同时具备低权用户 + 超户（或可切换角色） |
| 1058 完整 dblink | 靶机 → 攻击机监听端口出站可达 + 攻击机监听器 |

### 5.3 建议不做的默认动作

- 在**攻击机**上 `--local-container` 再声称「打的是远端靶机」  
- 在未授权/未白名单目标上开启 `local_lab` 宽网段扫描式连接  
- 把本地 marker 成功直接写成「完整 dblink 供应链打穿」

## 6. 推荐迁移路径（产品/工程）

按性价比排序：

### P0 — 远程目标模式（最高优先级）

```text
输入：ATTACK_ENV_TARGET_URL=tcp://靶机:5432
     或显式 database DSN
行为：跳过本机 compose（或仅作可选）
      直接 local_kb 抽取 execution_spec → 改写 host/port → 执行 → oracle → repro
```

验收标准：

- 同一 `execution_spec` 在本地 127.0.0.1 与授权远端 IP 上均可 `数据库命中`（网络/账号满足时）  
- `repro` 中明确记录 `target_host` 为远端地址  

### P1 — 策略与预检模板

- `authorized_target` + allowlist 命中结果写入 repro  
- 攻击机对靶机：TCP 探活 → 认证探活 → 失败归因（网络 / 前置 / 执行 / 证据）  

### P2 — 取证语义

- pcap 标注 `capture_side=attacker`  
- version_evidence 增加「claimed 来自 NVD；verified 来自远端 `version()` / 镜像若可知」  

### P3 — 1058 完整链（可选）

- 攻击机启动临时 listener  
- 动态改写 dblink 目标为攻击机可达地址  
- 出站失败单独归因，不与简化 marker 成功混写

## 7. 场景对照实验设计（建议后续做）

| 实验 ID | 拓扑 | 目的 | 期望 |
|---|---|---|---|
| E1 | 同机 127.0.0.1（基线） | 回归现有 3 CVE | 均 `数据库命中` |
| E2 | 攻击机 → 同网段靶机私网 IP，靶机跑 vulhub | 验证 DSN/策略/无本机 compose | 9193、1058 简化优先通过 |
| E3 | 同 E2，仅 2122 | 验证环境敏感漏洞跨机稳定性 | 可能 pass/fail 双结果，记环境指纹 |

| E5 | 错误白名单 / plan_only | 安全边界 | 必须 `策略拦截`，不得误执行 |

记录字段建议：拓扑、RUN_MODE、allowlist、target DSN（可脱敏）、往返时延、失败归因、pcap 侧、是否起本地 compose。

## 8. 风险与表述边界

### 8.1 技术风险

- 把「本地容器成功」外推为「生产靶机可打」  
- 2122 假阴性/假阳性随环境漂移  
- 跨机抓包为空被误判为利用失败（应用 oracle 优先）  
- 完整 1058 因 NAT 失败被误判为漏洞不存在  

### 8.2 合规边界

- 两机复现**仅限授权隔离环境**  
- `authorized_target` 白名单是硬闸，不是装饰  
- repro 与报告应写明目标范围与执行模式  

### 8.3 对外表述建议

**宜：**

> 在授权本地靶场完成数据库非 HTTP 自动闭环；协议执行器支持指向授权远端 DSN 的迁移实验。

**不宜：**

> 已支持任意远程靶机一键复现 / 已打穿完整 1058 外连带出链（当前未做）。

## 11. 收束

本地三个成功案例证明的是：

> **数据库协议利用可以结构化（execution_spec）、可判定（oracle）、可归档（repro），且不必伪装成 HTTP。**

迁到攻击机–靶机时：

> **利用语义大多可复用；编排与策略必须从「本机起靶」升级为「授权远端目标」。**  
> **能迁的是 payload 与 oracle；不能假装已迁的是默认 Docker 同机假设。**

下一步最有价值的工程动作不是再堆本地 CVE 数量，而是做出 **P0 远程目标模式**，并用 E2 对照实验证明：同一 execution_spec 在授权远端 IP 上仍可 `数据库命中`。
