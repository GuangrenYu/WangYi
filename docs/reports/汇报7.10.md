# CVE Hunter 多靶场建设阶段汇报（7.10）

**统计日期**：2026年7月17日（已完成历史反查）  
**统计对象**：`data/test_cases/未在工作流实现.txt`  
**目标**：评估厂商官网漏洞信息与历史未实现 CVE 的重合情况，并确定下一阶段可使用 Docker 部署真实软件靶场的实际规模。

---

## 一、结论摘要

本次统计得到三个核心结论：

1. **历史官网反查已从“下一步建议”变成可重复运行的程序，并实际命中 25 个唯一 CVE。**  共形成 80 条产品级候选：Oracle 73 条、Jenkins 1 条、Microsoft 6 条，来源错误为 0。
2. **25 个命中不等于 25 个可部署 Docker 靶场。**  当前结果中只有 1 条 Jenkins Docker 配方候选，但公告未解析出可固定的历史版本和精确安装包 URL；另有 73 条需 Oracle 授权介质、6 条需 Microsoft 隔离 VM，因此本轮官网反查新增的“已验证可运行环境”仍为 0。
3. **当前本机已经具备 11 条真实软件 Docker 靶场材料。**  这 11 条来自本地 Vulhub；补齐 Reapoc 后理论覆盖可提高到 32 条，其中净新增 21 条。

因此，“现在能做多少条”需要按落地状态回答：

| 口径 | 数量 | 含义 |
|---|---:|---|
| 官网历史公告对历史集合的唯一 CVE 命中 | 25 | 有官方漏洞和受影响产品证据，不代表环境已具备 |
| 官网历史反查新增已验证可运行环境 | 0 | 80 条候选的 `environment_status` 均为 `not_present` |
| 官网历史反查 Docker 配方候选 | 1 | Jenkins 候选，版本和精确介质尚未确认 |
| 当前本机已有真实 Docker 环境材料 | 11 | Compose 已在本地，可进入启动和验证阶段 |
| 补齐 Reapoc 后的真实 Docker 理论覆盖 | 32 | 11 条 Vulhub + 21 条 Reapoc 净新增 |
| 全部来源理论环境候选 | 42 | 还包含 8 条模拟环境和 2 条非 HTTP Metarget 场景，不能全部算真实 Docker 软件靶场 |

> “最新公告交集为 0”只描述旧的最新快照口径。历史反查的实际交集为 25，但当前最稳妥的建设基线仍是先完成 11 条本地 Vulhub 的端到端闭环，再落地 Reapoc 的 21 条净新增环境。不能把公告命中或 42 条理论候选直接报告为可运行靶场。

### 2.2 官网历史公告候选集合

官网发现结果来自：

- Oracle CVE-to-Advisory Mapping 定位历史 CPU/CSPU/Security Alert，再解析公告风险矩阵；
- Jenkins Security Advisory RSS 及 36 份历史 Core 公告正文；
- Apache Tomcat 7、8、9、10、11 五个分支的完整历史安全页；
- Microsoft MSRC 官方 OData 索引 9 页，再按命中月份获取 11 份 CVRF。

本轮实时采集结果为：

| 指标 | 数量 |
|---|---:|
| 输入唯一 CVE | 1228 |
| 历史反查命中唯一 CVE | 25 |
| 产品级候选记录 | 80 |
| Docker 配方候选记录/唯一 CVE | 1 / 1 |
| 需 Oracle 授权介质的记录/唯一 CVE | 73 / 18 |
| 需 Microsoft 隔离 VM 的记录/唯一 CVE | 6 / 6 |
| 本轮已验证精确安装包 URL | 0 |
| 本轮新增本地环境 | 0 |
| 来源错误 | 0 |

产品级记录数大于唯一 CVE 数，主要是因为同一 Oracle CVE 影响多个产品。统计官网覆盖时按唯一 CVE 计算，评估部署成本时按产品级候选计算。

### 2.3 “能做”的判定标准

程序现在分别记录 `environment_status`、`deployment_type` 和 `media_status`，不再用单一“公告可查”状态代替部署可行性：

| 状态 | 判定条件 | 是否计入当前真实 Docker 可做数 |
|---|---|---|
| 当前可落地 | 本地已有与 CVE、真实产品相符的 Compose | 是 |
| Docker 配方候选 | 官网给出受影响版本，存在官方真实产品镜像，但尚未生成或验证 Compose | 否，待实施后计入 |
| 商业介质人工准备 | Oracle 等产品需要支持合同、许可接受或客户安装介质 | 否 |
| 隔离 VM | Windows Server、SharePoint、Exchange、SQL Server 等需要未打补丁 VM 快照 | 否，不属于 Docker 主线 |

仅 CVE 编号相同但产品不同也不能算现成环境。例如 Oracle 产品内嵌 Spring 组件的 CVE 即使命中本地 Spring Compose，也不能证明已经获得对应 Oracle 产品靶场。

介质状态只对包含明确文件名和安装包扩展名的 URL 执行 `HEAD`。目录页、下载中心首页或产品介绍页即使返回 200，也不会标记为 `verified_download`；本轮 80 条候选中没有精确安装包通过该核验。

### 3.1 最新公告交集为 0 的旧口径说明

此前报告的 0 条来自“只抓最新公告”的快照，并非历史官网没有对应 CVE。两个集合时间范围不同：

- `未在工作流实现.txt` 是历史积压集合，主体为较早年份 CVE；

| CVE-2025-32395 | Vite | `third_party/vulhub/vite/CVE-2025-32395/docker-compose.yml` |

这 11 条代表“环境材料已在本地”，不等于 11 条已经全部端到端复现成功。仍需逐条验证：

- 镜像是否还能拉取或构建；
- 容器是否健康；
- 映射端口是否能被发包节点访问；
- 漏洞所需初始化数据、账号、插件或协议是否就绪；
- PoC 与目标侧 Oracle 是否能证明漏洞成功；
- 测试结束后是否完成容器回收。

其中 Airflow、cups-browsed、Ghostscript 等环境并非标准 HTTP Web 请求场景，可能需要消息协议、UDP、文件处理或其他执行器支持，不能仅凭 Docker 能启动就计入 HTTP 工作流成功数。

## 六、不计入真实 Docker 软件靶场的 10 条候选

### 6.1 vulnerability-poc 的 8 条模拟环境

该来源对历史集合净新增 8 条，但多数通过 Flask、SQLite 等重新实现漏洞路径和触发逻辑，不是原始受影响产品。它们可以用于流量生成和 IPS 规则测试，但不能作为真实产品漏洞复现证据，因此不计入本报告的真实 Docker 可做数。

### 6.2 Metarget 的 2 条净新增场景

Metarget 净新增 2 条主要属于容器、内核或基础设施场景，需要专用 Linux/root 节点，且不一定适用于当前 HTTP PoC 执行器。它们属于真实基础设施靶场方向，但不计入本轮 Docker Web 软件靶场主线。

## 七、下一步实施建议

### 第一优先级：完成本地 11 条环境基线

1. 修复 Docker daemon 当前不响应的问题。
2. 对 11 条 Compose 逐条执行“配置解析—镜像拉取/构建—启动—端口探测—健康检查—清理”。
3. 先将环境启动结果与漏洞利用结果分开统计，避免“容器启动成功”被误记为“漏洞复现成功”。
4. 为每条环境补齐 `environment_manifest.json` 中的产品版本、镜像摘要、端口、初始化步骤和回收结果。

### 第二优先级：落地 Reapoc 的 21 条净新增环境

1. 采用浅克隆或稀疏检出，只下载与 21 条 CVE 对应的目录。
2. 审计 Compose、Dockerfile 和启动脚本，不直接执行未经检查的第三方脚本。
3. 将真实产品环境统一接入现有 `docker_compose` launcher 和自动清理链路。
4. 完成后重新统计本地实际覆盖，理论目标为 32 条。

### 已完成：建立历史官网公告索引

1. Oracle：已解析 CVE-to-Advisory Mapping 的 `rowspan`，并按映射获取历史 CPU/CSPU/Security Alert。
2. Jenkins：已遍历历史 Core Security Advisory。
3. Tomcat：已解析 7、8、9、10、11 各分支完整历史安全页。
4. Microsoft：已使用官方 OData 分页索引定位月份，只获取命中月份 CVRF。
5. 已使用 1228 条 CVE 完成反向查询，实际得到 25 个唯一 CVE、80 条产品级候选。

下一步不是继续扩大公告数字，而是对这 25 个 CVE 做介质、版本和部署清单补齐。优先处理唯一的 Jenkins Docker 候选；只有确定受影响版本、精确安装包或镜像标签并成功启动后，才能从“候选”转为“可运行环境”。

## 八、阶段结论

历史官网反查已经证明，1228 条任务中有 25 个唯一 CVE 具备 Oracle、Jenkins 或 Microsoft 官方历史证据，但没有任何一条因此自动成为本地可运行靶场。对现有任务，真实 Docker 软件环境建设仍应以本地 Vulhub 11 条为起点，并以 Reapoc 净新增 21 条为下一扩展批次。

最终可执行口径为：

```text
当前本地真实 Docker 环境材料：11 条
补齐 Reapoc 后理论真实 Docker 覆盖：32 条
官网历史反查命中：25 个唯一 CVE / 80 条产品级候选
官网历史反查新增已验证可运行环境：0 条
旧的官网最新公告快照交集：0 条（仅作口径说明）
```

下一阶段的验收目标不应只是“发现 32 条”，而应是逐条形成可启动、可验证、可回收、可审计的真实产品靶场闭环。
