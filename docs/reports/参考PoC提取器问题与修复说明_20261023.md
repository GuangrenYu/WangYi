# 参考 PoC 提取器：问题、修复与残留风险

日期：2026-10-23  
范围：差距批中「我方参考正文里已有利用材料，却抽不成可发请求 / 抽到了却未优先发出」一类问题  
口径：只使用我方 `ref_cache` / 参考抓取正文；对方 YAML 仅作事后对照，不参与发包。

---

## 1. 现象

差距批失败里，有一类并不是「网上完全没材料」，而是：

1. 缓存页里已经出现路径、SQL/EL、JSON 等利用片段；  
2. 确定性提取结果为 **0**，流程落到 `local_kb_poc0911`；  
3. 或提取到了候选，但弱变体（如 `undeployment`）与完整利用一起轮询，最终落盘/观感像「好的没发出去」。

典型样本：

| CVE | 材料里已有什么 | 修复前行为 | 修复后小样本 |
|---|---|---|---|
| CVE-2018-16357 | Gitee README：`payload:field=1)/**/and/**/updatexml...`，并写明 `api.php/Cms/search` | extract=0 → 发 poc0911 的 `order=updatexml...` | **SUCCESS**，`reference_evidence`，发出 `field=...updatexml...` |
| CVE-2018-16621 | Loucy 脚本：`POST /service/extdirect` + `json.dumps(inject_data)` | extract=0 或仅空 GET → poc0911 的 `/service/rest/v1/users` | **SUCCESS**，`reference_evidence`，发出 Loucy 的 extdirect JSON |
| CVE-2019-0227 | 参考中已有 deployment 多步 | 能提取，但 undeployment 等弱候选随后也发；落盘常为最后一次弱请求 | 仍发我方证据；主证据可排到 primary，弱变体 secondary |

---

## 2. 根因（提取器）

提取入口：`extract_http_requests()`（`cve_hunter/poc_parser.py`），再经 `page_has_extractable_cve_http` / `_reference_http_evidence_candidates` 进入候选池。

修复前主要只认这些形态：

- 标准 raw HTTP 行（`GET/POST ... HTTP/1.1`）  
- curl  
- `requests.get/post("字面量 URL")`  
- 简单拼接路径、裸 `https://...?...`  
- `payload = '''SOAP...'''` + `requests.post(self.xxx, data=payload)`

**认不出、因而漏提的两类真实材料：**

### 2.1 叙述型 `payload:` 查询串（16357）

README 常见写法：

```text
via api.php/Cms/search
payload:field=1)/**/and/**/updatexml(... )#&keyword=title&scode=1
```

没有 `GET ... HTTP/1.1`，也不是 curl。旧逻辑整段跳过 → 候选池为空。

### 2.2 Python `json.dumps(变量)` + 嵌套 dict（16621）

脚本形态：

```python
exploit_url = f"{HOST}/service/extdirect"
inject_data = { "action": "coreui_User", ..., "roles": [el_expr] }
session.post(exploit_url, headers=..., data=json.dumps(inject_data))
```

旧逻辑问题：

- `post(...)` 参数匹配在 `json.dumps(...)` 的第一个 `)` 处被截断；  
- `inject_data = { ... }` 用非贪婪正则，嵌套花括号提前结束；  
- `el_expr` 多行 f-string 未展开进 JSON；  
- 仅抽到 `GET /service/extdirect`（无 body）时得分过低（&lt;5）被丢掉。

### 2.3 与「提示词禁止改写」的关系

提示词约束的是 **LLM 生成** 阶段。  
上述两条主路径在修复前根本 **没把完整 PoC 送进候选池**，提示词没有机会生效。  
因此需要 **提取器补形态 + 发送优先级**，不能只改提示词。

---

## 3. 如何修复

### 3.1 新增提取

1. **`_extract_payload_label_queries`**  
   - 识别 `payload:a=...&b=...`；  
   - 在上文定位路径（如 `api.php/Cms/search`）；  
   - 组装 `GET /path?query`。

2. **`_extract_python_json_dumps_posts`**  
   - 识别 `session/requests.post(url_var, ..., data=json.dumps(body_var))`；  
   - 用括号深度解析嵌套 `body_var = { ... }`；  
   - 解析 `el_expr = ( f"..." f"..." )` 等字符串变量并填回 dict；  
   - 产出 `POST /service/extdirect` + JSON body。

### 3.2 发送优先级（候选调度）

在 `graph.py`：

- 为候选标注 `dispatch_priority`：`primary` / `secondary`；  
- **primary**：多步、高置信、含 deployment / updatexml / extdirect 等完整利用；  
- **secondary**：`undeployment`、空探测、`poc0911` 等；  
- `_next_attempt_or_phase_update`：**先发完所有 primary，再发 secondary**。

这样「找到了完整 PoC 却先发弱请求」在调度层被压住（落盘 `poc.http` 仍可能是最后一次尝试，属落盘语义，不代表 primary 未发送）。

### 3.3 小样本验证（任务 `447308f236f7`）

| CVE | 结果 | 来源 |
|---|---|---|
| CVE-2018-16357 | SUCCESS，IPS CVE 字段命中 | `reference_evidence`（我方 Gitee README 提取） |
| CVE-2018-16621 | SUCCESS，IPS CVE 字段命中 | `reference_evidence`（我方 Loucy 提取） |
| CVE-2019-0227 | FAILURE | 仍走我方 `reference_evidence`；伴随 SSL/搜索噪音 |

结论：修复针对的是 **「我方材料 → 可发请求」**，不是照抄对方 YAML。

## 4. 还有没有类似问题

**有。** 同类风险按层归纳如下。

### 4.1 提取器仍可能漏掉的形态（高相似）

| 形态 | 风险 | 说明 |
|---|---|---|
| 图片/截图里的 PoC | 高 | OCR 未做，正文无字符串则永远抽不出 |
| 仅 PDF/附件 | 高 | 未进文本提取 |
| `httpx` / `urllib3` / Java `HttpURLConnection` 等非 requests API | 中高 | 未覆盖 |
| `data=json.dumps({...})` 匿名 dict 内联 | 中 | 当前偏「变量名 + 赋值」 |
| GraphQL / WebSocket / 二进制协议 | 高 | 超出当前 HTTP raw 假设 |
| 多步依赖登录 Cookie，但登录请求未抽出 | 中 | 可能只发出利用步，环境无会话 |
| Host 头为占位词（如 `Host: site`） | 中 | 已观察到 `urlsplit` 对非法 bracket host 抛错，可打断整页提取 |

### 4.2 调度与落盘（中相似）

- primary 已发送且失败后，仍会继续 secondary；**最终 `poc.http` 可能是弱请求**，易造成「没发好 PoC」的误判。  
- 需要看 verify 顺序 / pcap / attempt 记录，不能只看最终文件名对应内容。

### 4.3 材料与冲突过滤（中相似）

- 正确的 PoC 写在 **另一 CVE 的 vulhub 目录**（如 16621 材料在 CVE-2020-10204 下）时，冲突 CVE 过滤会丢弃——这是防串号，但会少一条来源。  
- 缓存命中旧空页、厂商反爬页时，「有 URL、无正文」仍会导致 extract=0。

### 4.4 提示词无法单独覆盖的部分

- 提取器不认识的语法 → 候选池为空 → 提示词无输入可保真。  
- 设备侧「同请求仍无当前 CVE 字段」→ 属 IPS 规则/归因，不是提取器问题。

## 5. 第二轮增强（2026-10-23 晚，终止全量后）

对差距批 219 条缓存扫描：修复前约 **34** 条能抽出候选；「正文有利用痕迹但候选为空」约 **147** 条。高频漏提格式包括：`browser_url_qs`、`path_mention`、**extract 非空却被过滤**、`curl`、`raw_http`、`powershell`、`requests(sys.argv+path)`、`multipart` 等。

本轮针对性补强：

| 增强 | 覆盖 |
|---|---|
| `requests.*(sys.argv[N]+"/path", data=var)` + `urllib.urlencode` | WordPress/JobHunt 等脚本 |
| `curl -F files=@... http://.../server/php/` | jQuery File Upload 类 |
| 路径字面量 `"/flex2gateway/amf"` + Content-Type | ColdFusion AMF 等 |
| Invoke-WebRequest 基础解析 | PowerShell 片段 |
| 双 CVE 写死评分不再一刀切 -25 | 19487/19488 等同文双编号 |
| CVE 缓存页强请求放宽入库 | exploit-db 正文未写 CVE 号 |
| 非法 Host 容错 | 避免整页提取崩溃 |

回归抽查：`10653`→`PUT /zdm/ios/mdm`；`19487`→`POST .../admin-ajax.php`；`8739`→`POST /server/php/index.php`；`3066`→`POST /flex2gateway/amf`。全量可抽出候选约 **34→53**。

仍空的常见原因：截图/PDF、仅叙述无路径、冲突 CVE 页、登录态多步未拼全、AMF 二进制 body 无法忠实还原等——这些不是再加一两条正则就能全部覆盖。

## 6. 建议的后续动作

1. 用增强后的提取器 **重跑差距批全量**，对比 `reference_evidence` 成功数。  
2. 对仍 extract=0 且 `miss_with_hint` 的样本继续按格式记账（见 `output/audits/gap_extract_miss_formats.json`）。  
3. 结果汇报区分「primary 是否已发送」与「最终 poc.http 内容」。  
4. 若提取器收益见顶，再考虑「提取为空时 LLM 读原文补候选」作为第二道防线（本次按你的选择先强化提取器）。
