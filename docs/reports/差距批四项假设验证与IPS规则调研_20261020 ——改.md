# 差距批的四项假设：已做的测试与下一步方向

> 组会报告日期：2026-10-20；正文约 4—5 分钟。数据截于 2026-10-19 23:20（北京时间），当前批次仍在运行。文末附核验依据，供问答时查阅。

## 1. 问题与评价标准

本次围绕固定的 **219 个差距 CVE** 展开：对方任一设备成功，而我方此前未成功。当前成功标准是：**新华三或迪普任一设备的日志 CVE 字段包含当前编号**。衡量的是 IPS 的 CVE 归因能力，不能据此证明靶机漏洞利用成功。

针对差距，我依次考察了四种可能：**爬虫证据不足、提示词约束不足、模型选择、IPS 规则触发与 CVE 关联**。前三项已做测试，第四项完成了资料调研，尚待实验验证。

## 2. 假设一：爬虫没有获取到足够证据

历史诊断中，219 条里有 **95 条未在缓存找到对方关键路径，58 条虽有路径或相关证据，却没有用于最终请求**。这是定位线索，不等于已经确认根因。

随后修复了来源发现、源码跟进、GitHub 限流回退、正文截断和 HTML PoC 源码被清洗等问题。证据获取与保留确有改善，但需要区分统计口径：

- 早期对 **326 个分设备差异 CVE** 的离线评估中，**90 个**有更多完整代码块、**104 个**有更多条件原文进入提示词。“一百左右”对应信息利用改善，并非新增成功数，两项也不能相加。
- 后续针对原先缺路径的 **95 条**真实抓取回归，**49 条**找到对方完整路径，**24 条**取得完整公开 PoC 源文件；去重后 **52 条**至少满足一项。这仍只是材料覆盖，尚非有效利用或 IPS 命中证明。

**阶段判断：爬虫确实是一个瓶颈，修复有收益；但“拿到材料→形成正确请求→触发当前 CVE”之间仍有缺口。**

## 3. 假设二：提示词没有把要求说具体

第一轮把双方请求差异总结为生成和审查约束。实际提示词中的主要内容为：

```text
路径：保留完整层级与部署前缀；禁止缩成目录或只留 basename。
禁止用同产品兄弟接口替换证据中的精确 endpoint。
方法与 query/body 承载位置与证据一致，不得互换。
Payload 完整（含编码、重复参数）；禁止简化或清洗。
同时有叙述与 raw/curl/nuclei 时，以完整请求块为准。
无完整 method/path/参数证据则返回空数组；禁止编造。
```

另要求保留 Nuclei 模板的变量、提取器和多步依赖。改前、改后**共同完成的 26 条中，均为 5 成功、21 失败，没有失败转成功**。

第二轮加入设备与验证前提，原文为：

```text
验证环境：流量经迪普、新华三 IPS 检测。
成功条件：至少一侧日志里 CVE 列表/字段包含当前 {cve_id}。
通用攻击名（SQL注入、命令注入、XSS 等）不算成功。
必须保留证据里的特征触发点（完整 path、参数、编码、多步 body），
不要收成仅能触发通用告警的弱探测。
```

与上一批共同完成的 **32 条均为 7 成功、25 失败**，也未观察到新增成功。两轮均中途取消，因此只能说：**已完成的交集样本未显示收益，不能断言提示词对全量无效。**

## 4. 假设三：模型选择影响了结果

将 `grok-4.5` 换为 `deepseek-v4-pro-0813`；型号以调用记录为准。相同设备前提提示词下，两批共同完成的 **32 条仍为 7 成功、25 失败**。

**目前没有看到换模型带来明显改善。**但部分请求直接来自本地库或确定性提取，未经过模型生成；此外还存在网络失败、缓存和运行版本差异。这不是严格的模型能力对照，不能据此认定两模型能力相同。

## 5. 假设四：IPS 规则触发条件或 CVE 关联影响识别

**这是有技术依据、值得验证的方向，但现有日志不足以确定原因。**

新华三配置文档说明，IPS 先识别应用协议、提取报文特征，再匹配特征；其自定义规则可检查方法、协议字段、内容及偏移范围，并要求多个检查项同时满足。迪普也公开说明采用攻击特征库和协议语义解析。[R1][R2] 因此，请求即使触发了某类攻击告警，也可能缺少另一条关联当前 CVE 的规则所需条件。公开资料没有披露本实验涉及的厂商预定义规则，不能直接推定缺的是哪个字段。

另一个关键点是：**CVE 可以是规则关联的信息，并非设备在流量中“读出了 CVE 编号”**。公开 IDS 文档展示了 HTTP 检查条件与 CVE 引用分别定义的机制；这里只用于解释原理，不代表两家厂商内部实现。[R3][R4]

本地数据也需要更准确地描述：10 月 16 日批次的 **149 条失败中，72 条为“仅通用检测”，占 48.3%，是最大类别，但并非绝大多数**。而程序把“CVE 字段为空”和“字段列出其他 CVE”都归入该类。例如 `CVE-2019-0227` 的该批结果实际是**命中了其他 CVE**，不能仅凭状态名称认定设备只触发了通用规则。

所以，先前加入设备信息的思路有合理出发点；但品牌名称和成功标准不能提供具体规则条件，单靠提示词难以解决。

## 6. 相似 PoC 对照：对方成功、我方失败的常见差异

为解释“对方能命中当前 CVE、我方不能”是否主要来自**请求本身不同**，将对方成功产物（`只准看不准用/运行结果(1323个)/poc` 中的 YAML/raw HTTP）与我方多批落盘结果（优先 `a349fd259aa4`、`abbcd88ecf54` 等）中**失败**条目做路径与 payload 对照。并集口径约 **148 条失败**（另有约 20 条我方已成功，不纳入本对照）。分类按首条可解析请求的 method/path/query/body 近似比较，不声称覆盖全部多步细节。

### 6.1 分类统计

| 差异类型 | 约数量 | 含义 |
|---|---:|---|
| 路径不同 | 71 | 对方打漏洞接口，我方打了兄弟路径、弱化路径或完全不同的 endpoint |
| 同路径、payload 不同 | 32 | path 对齐，但参数名、注入点、编码或 body 与对方不一致 |
| 我方无有效请求 | 16 | 对方有可解析请求，我方未产出可发 raw HTTP |
| 同路径、方法不同 | 9 | 如对方 GET 我方 POST，或对方 POST 我方 GET/PATCH |
| 同路径仍失败（含仅通用 IPS） | 16 | 请求已很接近，仍无当前 CVE 字段命中 |
| 对方产物未能解析 | 2 | 对照侧无抽出标准 HTTP 行 |

**解读：** 约 **七成以上**失败（路径不同 + payload 不同 + 无请求 + 方法不同）可先归因于**发出的请求与对方成功请求不一致**；约 **一成**属于“请求已接近仍不命中”，更适合用第 5 节的规则/归因假设解释，而不能再简单归为“没爬到”。

### 6.2 典型对照（对方成功 vs 我方失败）

**（1）路径不同——打错接口**

| CVE | 对方（成功） | 我方（失败） | 说明 |
|---|---|---|---|
| CVE-2018-16621 | `POST /service/extdirect`，body 含 `previewAssets` + EL 表达式 | `POST /service/rest/v1/users`，另一套用户创建 + EL | 同属 Nexus 生态，**兄弟 API**；对方走 ExtDirect 预览接口 |
| CVE-2018-10653 | `PUT /zdm/ios/mdm` + XXE DTD | `POST /zdm/cxf/services/AdminService` + 另一 XXE | 产品前缀相近，**具体资源与方法不同** |
| CVE-2014-8072 | `GET /openmrs-standalone/admin` | `GET /admin/` | **丢掉部署前缀** `openmrs-standalone` |
| CVE-2014-8739 | `POST /server/php/` 上传 webshell | `GET /server/php/files/...php` 直接读文件 | 对方是**上传步**，我方跳到**已上传后的读取**，特征面不同 |

**（2）同路径、payload 不同——注入点或编码不一致**

| CVE | 对方（成功） | 我方（失败） | 说明 |
|---|---|---|---|
| CVE-2018-16357 | `/api.php/Cms/search?field=1)/**/and/**/updatexml(...)` | 同 path，但 `order=updatexml(...)` | **参数名从 field 换成 order**，签名可能只认 field 链 |
| CVE-2019-0227 | `GET .../AdminService?method=...deployment...`（部署 WSDD） | 同 path，但 `method=...undeployment...` | 同接口，**部署 vs 卸载**；对方成功链含部署特征 |
| CVE-2019-13063 | `script=/../../../../../../etc/passwd`（明文 `../`） | `script=%2e%2e%2f...`（全 URL 编码） | 规范化前后特征可能不一致 |
| CVE-2019-10352 | multipart 字段名 `dir/../../../pwned` | 字段名 `FILE`，filename 普通名 | **目录穿越写在字段名**，我方未保留该形态 |

**（3）同路径、方法或 body 缺失**

| CVE | 对方（成功） | 我方（失败） | 说明 |
|---|---|---|---|
| CVE-2013-2068 | `GET /agent/log?filename=../...&data=...` | `POST /agent/log`，body 另一套 filename | **方法与参数承载位置**均变 |
| CVE-2019-9580 | `POST /api/v1/executions` + JSON 远程命令 | `GET /api/v1/executions` 空 body | 方法弱化、**丢掉利用 body** |
| CVE-2019-16068 | `POST .../manage_files.cgi` 完整 multipart 升级包 | `POST /manage_files.cgi` **空 body** | 路径还被缩短，payload 丢失 |
| CVE-2020-27232 | `POST .../main.do` + `FindServiceUid=1' AND SLEEP(5)-- -` | 同 path/query，**body 为空** | 路径对齐但 **SQL 特征在 body 中丢失** |

**（4）请求已很接近仍失败（需结合 IPS 归因）**

| CVE | 对照摘要 | 说明 |
|---|---|---|
| CVE-2001-0987 | 双方均为 `GET /cgi-bin/cgiwrap/%3CS%3E` | 路径与编码一致，我方仍报“仅通用/CVE 字段不匹配” |
| CVE-2012-0551 | 双方 `lifecycleEdit.jsf?appName=...alert...` 一致 | 同上，更支持**规则版本/启用/CVE 关联**差异，而非“没找到路径” |
| CVE-2017-3066 | 双方 `POST /flex2gateway/amf` + 相同 hex body | 请求高度一致仍失败时，应查设备侧规则 ID 与 CVE 字段，而不是继续改提示词空转 |

**（5）我方无请求**

对方仍有明确 raw（如 `GET /log_download.cgi?type=../../etc/passwd`），我方结果无 `poc.http` 或未生成候选，常伴随资料抓取 SSL 失败、无 PoC。此类首先是**材料与候选生成缺口**，不是 IPS 误判。

### 6.3 综合解释：为什么“他们成功、我们失败”

在固定成功标准（日志 **CVE 字段含当前编号**）下，对照支持如下分层，而不是单一原因：

1. **请求形态未对齐（主因，可观测）**  
   对方成功 YAML 提供了可触发其实验环境的 method/path/payload；我方大量失败最终源仍是 `local_kb_poc0911` 或错误候选，表现为兄弟路径、缺部署前缀、缺 body、参数名/编码/方法被改写。这类差异会直接改变 IPS 可见特征，足以解释“对方有当前 CVE、我方只有通用名或其他 CVE”。

2. **请求已接近仍不命中（次因，需设备侧核验）**  
   少数样本双方 path/query/body 高度一致仍失败，不能再用“没爬到”概括；更符合第 5 节：多条件规则、特征库版本、CVE 关联字段或日志采集差异。

3. **与四项假设的对应关系**  
   - 爬虫/证据：解释“无请求、路径缺失、未用上缓存中的精确 endpoint”。  
   - 提示词/生成/选型：解释“有材料仍简化 payload、换参数、换方法”。  
   - IPS 规则与归因：主要解释“同请求仍无当前 CVE 字段”的少数样本，以及“通用 IPS / 命中其他 CVE”的日志语义。

4. **不能从本对照推出的结论**  
   对方成功不自动证明其 YAML 在本实验室特征库与策略下也可复现；我方失败也不自动证明靶机无漏洞。本对照只说明：**在已落盘的请求文本层面，双方经常不是在发同一条利用。**

### 6.4 对后续实验的直接含义

- 优先挑 **同 path 不同 payload** 与 **路径不同但产品相同** 的样本，把我方请求改到与对方 YAML 逐字段一致后重放，观察 CVE 字段是否出现。  
- 对 **已一致仍失败** 的样本，固定策略与特征库，导出规则 ID / 规则名 / CVE 列表，区分请求问题与设备配置问题。  
- 继续禁止在无证据时编造路径；对照目的是**对齐已有成功请求形态**，不是学习“为过设备而编造”。

## 7. 下一步

下一步应优先验证“**请求差异、规则命中、日志归因**”之间的关系：选取已有证据但未匹配当前 CVE 的少量样本，固定设备策略、特征库版本和发送条件；核对实际发出的报文与原始告警中的规则 ID、名称、CVE 字段，区分**请求条件不足、规则未启用或版本不同、CVE 关联或日志采集问题**。已有历史成功记录与第 6 节 PoC 对照可作选样依据，但仍需确认当前环境条件一致。

继续保留证据保真约束；待当前批结束后，再按相同样本复核结果，避免用不同完成进度的成功总数判断效果。对“同请求仍失败”与“请求明显不一致”两类样本应分开记账，避免把第 6 节已能解释的差异重新算进模型或提示词无效。
