## 2. 节点详解

### 2.1 validate_input
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_validate_input` |
| 作用 | 校验 CVE 编号格式（`CVE-\d{4}-\d{4,}`） |
| 怎么做 | 正则匹配，格式错误直接终止 |
| 调用 LLM | ❌ |

---

### 2.2 query_nvd
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_query_nvd` → `tools/nvd.py:query_nvd` |
| 作用 | 查询 NVD API，获取漏洞描述、CVSS 分值、受影响产品、参考链接 |
| 怎么做 | HTTP GET `api.nvd.nist.gov`，解析 JSON；本地有 NVD 镜像时优先读本地 |
| 调用 LLM | ❌ |

---

### 2.3 vuln_type_check ★LLM
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_vuln_type_check` → `classifier.py:classify_http_vuln_from_info` |
| 作用 | 判断漏洞是否属于 HTTP/Web 或数据库协议，决定后续执行路径 |
| 怎么做 | 把 NVD 描述 + 受影响产品 + CVSS 发给 LLM，要求输出 `is_http_vuln`、`vuln_type`、`protocol` |
| 输出 | `protocol = "http" \| "database" \| 其他` |
| 分支 | `database/http` → 继续；其他 → 输出「协议未支持」并跳到 generate_report |
| 调用 LLM | ✅ `invoke_llm(分类 prompt)` |

---

### 2.4 environment_agent
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_environment_agent` → `agents.py:run_environment_agent` |
| 作用 | 发现本地 vulhub/vultarget compose 文件，按配置拉起靶场容器 |
| 怎么做 | 1. 扫描 `third_party/vulhub` 索引，按 CVE 编号匹配 compose；2. 若 `local_container_mode=True`，执行 `docker compose up`，健康检查端口；3. 宿主机端口冲突时自动写临时 compose 重映射空闲端口 |
| 输出 | `target_url`、`target_host`、`compose_file`、`setup_result` |
| 调用 LLM | 可选（`AGENT_LLM_ENABLED=true` 时）；默认走确定性规则 |

> **端口冲突自动处理**：`_compose_with_free_host_ports` 检测宿主机占用端口，写临时 yml，映射到随机空闲端口后再启动。  
> **Windows CRLF**：`*.sh` entrypoint 自动 CRLF→LF，避免容器内 `$'\r'` 报错。

---

### 2.5 local_kb_search
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_local_kb_search` → `tools/local_kb.py:search_local_kb` |
| 作用 | 以**最高优先级**在本地知识库搜索已有 PoC，命中直接跳验证 |
| 怎么做 | 按优先级查：① `poc_kb/custom/`（自验证） → ② `poc_kb/trickest-cve/`（外部 PoC 目录）→ ③ vulhub README SQL 块；对 DB 路径调 `db_spec.extract_database_execution_spec` 抽取 execution_spec |
| 输出 | `raw_http` \| `execution_spec` \| `yaml_content` \| 未命中 |
| 调用 LLM | ❌ |

---

### 2.6 reference_analysis
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_reference_analysis` → `tools/web_extract.py` |
| 作用 | 爬取 NVD References 中的链接，提取网页正文内容，供后续 LLM 使用 |
| 怎么做 | 最多取前 8 个 URL，httpx 拉取，提取正文最多 3000 字符/条 |
| 调用 LLM | ❌ |

---

### 2.7 trigger_agent ★LLM
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_trigger_agent` → `agents.py:run_trigger_agent` |
| 作用 | 从 CVE 描述抽象出攻击规划：触发逻辑、攻击目标、前置条件、变量槽、验证提示 |
| 怎么做 | 把 CVE 描述 + 漏洞类型 + 受影响产品发给 LLM；输出结构化攻击规划，用于指导 PoC 生成 |
| 输出 | `trigger_logic`、`attack_objective`、`preconditions`、`variable_slots`、`validation_hint` |
| 调用 LLM | ✅ `invoke_llm(TriggerAgent prompt)` |
| 降级 | LLM 失败时退回确定性占位，主链路不中断 |

---

### 2.8 poc_from_refs ★LLM
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_poc_from_refs` |
| 作用 | 把参考页面内容喂给 LLM，让其生成 raw HTTP PoC |
| 怎么做 | `prompt = POC_GENERATION_FROM_REFS.format(...)` → `invoke_llm(prompt)` → 解析 JSON，提取 HTTP 候选 |
| 置信度 | 0.65（LLM 基于参考内容生成） |
| 调用 LLM | ✅ |

---

### 2.9 nuclei_search / exploitdb_search / imfht_search
| 节点 | 来源 | 怎么做 | LLM |
|---|---|---|---|
| nuclei_search | 本地 `nuclei-templates/` | 按 CVE ID 匹配 YAML 文件 | ❌ |
| exploitdb_search | Exploit-DB API | HTTP 查询 + 爬取 exploit 页面 + 提取 HTTP PoC | ❌ |
| imfht_search | imfht 漏洞库 | HTTP 查询漏洞页面 + 提取 HTTP PoC | ❌ |

三者均为**确定性搜索**，无 LLM。命中即提交候选，未命中依序回退。

---

### 2.10 web_search ★LLM
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_web_search` → `tools/web_search.py` |
| 作用 | 联网搜索 CVE 利用信息，再让 LLM 从搜索结果生成 PoC（兜底手段） |
| 怎么做 | 1. 调搜索 API 获取结果摘要；2. 拼 `POC_GENERATION_FROM_SEARCH` prompt + 搜索文本 → LLM |
| 置信度 | 0.45（最低，联网+AI 生成不确定性高） |
| 调用 LLM | ✅ `invoke_llm(POC_GENERATION_FROM_SEARCH)` |

---

### 2.11 verify_poc（核心执行节点）
| 项 | 内容 |
|---|---|
| 文件 | `graph.py:node_verify_poc` → `verification.py` |
| 作用 | 综合 Critic 审查 + 实际执行 + 结果判定 |

内部分三步：

**① CriticAgent（可选 ★LLM）**
- 文件：`agents.py:run_critic_agent`
- 作用：审查候选 PoC 合理性，检查格式错误、缺失字段，调整置信度，补充 `trigger_id` / `validation_hint`
- LLM：可选（`AGENT_LLM_ENABLED=true` 时调用，失败退回规则）

**② RequestExecutor（执行，无 LLM）**
- 文件：`verification.py:RequestExecutor.execute`
- HTTP 路径：→ `tools/http_sender.py:send_poc_and_capture`  
  - 优先走 `http2pcap` 服务（同步发包+抓包）  
  - 不可达时自动回退 builtin `httpx` 直连
- Database 路径：→ `executors/base.py:execute_spec` → `executors/database.py:execute_database_spec`  
  - 按 `engine`（mysql/postgres）选驱动  
  - 执行顺序：schema_sql → setup_sql → trigger_sql → cleanup_sql  
  - 执行前后用 `dumpcap` 抓 TCP 流量（`tools/tcp_capture.py`）

**③ SuccessOracle（判定，无 LLM）**
- 文件：`verification.py:evaluate_success`
- 判定层级：
  - IPS 精确命中当前 CVE → `检测命中`
  - 目标侧响应 oracle（状态码/响应体/DB 结果）→ `目标命中` / `数据库命中`
  - 仅通用 IPS 命中 → `仅通用检测`
  - 均未命中 → `无利用证据`

| 调用 LLM | CriticAgent 可选；RequestExecutor 和 SuccessOracle ❌ |

---

|---|---|
| 文件 | `graph.py:node_generate_report` |
| 作用 | 生成人类可读的分析报告，然后把成功 PoC 保存到本地 KB |

| 调用 LLM | ✅ `invoke_llm(ANALYSIS_REPORT)` |

## 3. LLM 调用汇总

| # | 节点 | 调用目的 | prompt 模板 | 是否必须 |
|---|---|---|---|---|
| 1 | vuln_type_check | 判断协议类型（HTTP/DB/其他） | 内联 prompt | 是（失败按 HTTP 继续） |
| 2 | trigger_agent | 生成攻击规划结构 | `TriggerAgent prompt` | 否（失败回退占位） |
| 3 | poc_from_refs | 基于参考页面生成 PoC | `POC_GENERATION_FROM_REFS` | 否（失败跳下一源） |
| 4 | web_search | 基于搜索结果生成 PoC | `POC_GENERATION_FROM_SEARCH` | 否（兜底） |
| 5 | verify_poc (Critic) | 审查候选质量/调整置信度 | `CriticAgent prompt` | 否（失败透传原候选） |
| 6 | generate_report | 生成归档分析报告 | `ANALYSIS_REPORT` | 否（失败跳过报告） |
| 7 | environment_agent | 环境规划辅助 | `EnvironmentAgent prompt` | 否（默认关闭） |

> 所有 LLM 调用均通过 `cve_hunter/llm.py:invoke_llm` 统一入口，  
> 模型由 `.env` 的 `LLM_MODEL` / `LLM_BASE_URL` 配置（默认 deepseek-v4-pro）。  
> 失败时抛异常，上层节点捕获后降级或跳过，**不会中断整条主链路**。

## 4. 数据流（State）

```
CVEState（LangGraph 共享状态）
  │
  ├─ cve_id / nvd_description / affected_products / cvss_score
  ├─ is_http_vuln / vuln_type / protocol
  ├─ attack_environment（target_url, compose_file, setup_result）
  ├─ poc_candidates[]（raw_http / nuclei_yaml / execution_spec）
  ├─ current_candidate_index
  ├─ attempt_history[]（每次发包+oracle 结果）
  ├─ ips_matched / target_oracle_success / success_level
  ├─ status_code（中文：目标命中/数据库命中/检测命中/...）
  ├─ success_tier（可复现归档/目标证据/已执行/连通/无）
  ├─ failure_class（输入/情报/环境/执行/证据/...）
  ├─ pcap_file_path
  ├─ repro_bundle_path / repro_bundle_complete
  ├─ agent_trace[]（各 agent 操作日志）
  └─ milestones{}（各检查点状态，用于分层统计）
```

## 5. 非 HTTP 数据库路径（专用子流程）

```
local_kb_search 命中 execution_spec
        │
        ▼
verify_poc → RequestExecutor.execute(execution_spec)
        │
        ▼
executors/base.py:execute_spec  →  executors/database.py:execute_database_spec
        │
        ├─ engine=mysql  → PyMySQL 连接 TCP:3306
        └─ engine=postgres → psycopg2 连接 TCP:5432
                │
                ├─ action=auth_bypass  → 反复登录测鉴权绕过
                ├─ action=multi_session → 双会话（低权植入+超户触发）
                └─ 普通 SQL → schema_sql → trigger_sql → cleanup_sql
                        │
                        ▼
              tcp_capture（dumpcap 抓 TCP 流量）
                        │
                        ▼
              oracle 判定（error_pattern / result_contains / auth_success）
                        │
                        ▼
              finalize_capture → data/cve/pcaps/<日期>/CVE-XXXX-XXXXX.pcap
```
